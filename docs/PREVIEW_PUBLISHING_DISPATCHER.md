# Sanity-to-protected-preview publishing preparation

Status: **non-deployed code only**. `scripts/preview-publishing-webhook.mjs` is a testable, fail-closed dispatcher. Its unit tests use synthetic signed payloads and a mocked deploy-hook fetch. It is not a running Worker, Sanity webhook, Pages hook or active publication path. No secret, hook URL, account token or customer data is in source.

The intended boundary is Sanity project `zavdffj8`, dataset `production` (a dataset name, not the production website), document types `editorialEntry`, `researchPublication`, `professionalAchievement`, and a Cloudflare Pages deploy hook bound **only** to a verified non-production branch. Cloudflare Pages project `dr-olaosebikan-git` has production branch `main`; this code must never receive a hook bound to `main`. The new handler checks a raw-body HMAC-SHA256 `sanity-webhook-signature` with a five-minute window, validates the small projected body, and requires an atomic durable `claim(idempotency-key)` before making one POST to the configured Pages hook. It accepts both publish and unpublish/delete notifications by triggering a fresh snapshot build, whose existing publication policy determines the exported content. It does not trust the webhook body as page content.

To make this operational later: (1) verify the chosen preview branch is present in the Pages Git binding and Access still blocks unauthenticated preview visitors; (2) create a Pages deploy hook restricted to that preview branch and store its URL as a secret; (3) provide a durable atomic claim store, with retention and a manual recovery procedure for failed/uncertain triggers; (4) deploy the dispatcher with request logs/traces and a secret Sanity signing key; (5) configure a Sanity **document** webhook for create/update/delete on only those three types, published documents only, project/dataset production, projection limited to `projectId`, `dataset`, `documentType`, `documentId`; (6) test one synthetic nonmedical publish and withdrawal on the protected preview and inspect both Sanity message/attempt logs and Cloudflare build/deployment status; (7) reconcile missed events by a manual or scheduled comparison of the latest eligible Sanity snapshot with the preview deployment. No hook, binding, Worker or scheduler was created here.

The exact projection and signature header must be checked against a real nonmedical webhook sample before activation. Sanity documents that unpublish generates a delete event and that at-least-once deliveries can retry twice after 30 seconds. A `502` returned after a failed/uncertain Pages hook call can therefore cause Sanity to deliver the *webhook* again; the consumed idempotency claim prevents a second automatic Pages-hook POST. That leaves the preview potentially stale until inspected and manually reconciled. A 202 means only that Pages accepted a build trigger, **not** that a build completed, Access remained effective or the content was visible. Production remains unchanged.

Sources: [Sanity webhook best practices](https://www.sanity.io/docs/content-lake/webhook-best-practices), [Sanity GROQ-powered webhooks](https://www.sanity.io/docs/content-lake/webhooks), [Cloudflare Pages deploy hooks](https://developers.cloudflare.com/pages/configuration/deploy-hooks/). Both vendors' current guidance was checked on 2026-10-12. Sanity's Growth trial status is owner-reported; no plan or subscription change was made.
